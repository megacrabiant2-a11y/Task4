# Реализация архитектур обработки данных: Lambda vs Kappa

Данный проект демонстрирует практическое различие между Лямбда и Каппа архитектурами на примере обработки логов просмотров книг в реальном времени.

## Сравнение подходов


| Критерий | Lambda Архитектура | Kappa Архитектура |
| :--- | :--- | :--- |
| **Количество конвейеров** | Два (Speed Layer + Batch Layer) | Один (Единый Stream Processor) |
| **Хранение истории** | В файлах/HDFS (для пакетного слоя) | Внутри распределенного лога сообщений |
| **Задержка (Latency)** | Низкая на Speed слое, высокая на Batch | Минимальная (миллисекунды в реальном времени) |
| **Сложность кодовой базы**| Высокая (нужно писать код для двух слоев)| Низкая (один скриншот/приложение для всего) |

---

## Порядок запуска

### Шаг 1: Поднятие инфраструктуры Redis
Создайте локальную папку `data` (нужна для логов): `mkdir data`
Соберите и запустите Redis-брокер:
```bash
docker build -t data-broker .
docker run -d --name redis-broker -p 6379:6379 data-broker
```

### Шаг 2: Запуск генератора логов
Откройте **Терминал №1** и запустите непрерывную генерацию событий:
```bash
python generator.py
```

### Шаг 3: Запуск слоев обработки
* **Для тестирования Лямбды (Speed слой):** Откройте **Терминал №2** и запустите `python lambda_speed.py`. Вы увидите мгновенную реакцию на события.
* **Для тестирования Лямбды (Batch слой):** Спустя 1-2 минуты генерации, запустите в **Терминале №3** команду `python lambda_batch.py`. Она прочитает файл, выдаст точную статистику за всё время и завершится.
* **Для тестирования Каппы:** Остановите предыдущие слои, откройте **Терминал №4** и запустите `python kappa_processor.py`. Он автоматически подтянет историю из Redis Stream с самого первого сообщения и продолжит обновлять ее на лету.
